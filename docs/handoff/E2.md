# Module E2 handoff: API routes, auth, provisioning, SDK

Owner paths: `apps/api/**` (except `main.py`), `services/auth/**`, `packages/client/**`,
`db/migrations/versions/0006_api.py`, `packages/core/tests/module_e2/**`.

## 1. Requests for the integrator (files E2 may not edit)

### 1.1 Console script (packages/core/pyproject.toml)
```toml
[project.scripts]
ragforge-admin = "ragforge_core.apps.api.admin:run"
```
Usage: `ragforge-admin create-tenant --name acme --owner "Ada" [--kind team --team-consent]
[--platform-admin] [--key-name owner]`.
It prints `tenant_id`, `user_id`, `scopes`, `api_key` once on stdout. It uses the `rf_api` role.
- Without `--platform-admin` the key gets the owner scopes (read, write, chat, approvals:write).
- `--platform-admin` adds `admin` (may provision other tenants). Give it to the operator only.
- A database error prints only its SQLSTATE (exit 3), never the driver message (bound params).

### 1.2 Wire these ports on `bootstrap.ApiContainer` (Phase 2)
The routes read ports from `app.state.container` **by attribute name**. A missing port returns
503 "Service not configured" instead of crashing. Add these fields to `ApiContainer` and fill
them in `build_api`:

| attribute | type | owner |
|---|---|---|
| `tx` | `TransactionManager` | exists |
| `secrets` | `SecretBox` | exists |
| `jobs` | `JobQueue` | A |
| `retriever` | `Retriever` | B |
| `embedders` | `EmbedderRegistry` | B |
| `agent` | `AgentRunner` | D |
| `sanitizer_factory` | `Callable[[], OutputSanitizer]` | E1 (`agent/sanitize.py`) |

`sanitizer_factory` is a **factory**: the API creates one sanitizer per answer, plus one each
for a replacement answer and for each rejected verification claim.

### 1.3 Resources
- Each API process opens **one extra** Postgres connection (role `rf_api`, autocommit) outside
  the SQLAlchemy pool. It runs `LISTEN rf_job_progress` (`apps/api/jobfeed.py`, started in the
  app lifespan). Size `max_connections` for it.
- Optional settings (`config.py`), currently hard-coded defaults in `deps.JobStreamConfig`:
  - `job_sse_poll_interval_s = 2.0`
  - `job_sse_keepalive_s = 15.0`
  - `job_sse_reauth_s = 30.0` (an open job stream re-checks that its key is unrevoked)

### 1.4 API engine: `hide_parameters=True` (db/engine.py)
Please create the `api` engine with `create_async_engine(..., hide_parameters=True)`. E2 maps the
expected data-rule errors (22023, 23514) to 422 and the CLI prints only the SQLSTATE, but any
other `DBAPIError` that reaches a log carries its bound parameters (e.g. an API key prefix and
digest on `api_keys` inserts). With `hide_parameters` the message never contains them.

## 2. Proposed contract changes (not applied; current code works without them)
1. **`ApiKeyCreate.client: Literal["ui", "mcp", "service"]` (required, no default).** The contract
   has no way to say who holds a key. Until it does, the NAME classifies it, and both rules fail
   closed (`services/auth/scopes.py`):
   - **MCP:** any name containing `mcp` (case-insensitive substring: "MCP server", "claude-mcp",
     "mcpserver", "ui:mcp") is an MCP key. A false positive only costs human-only scopes.
   - **Human:** `approvals:write` / `admin` are granted to an API-minted key only if its name
     declares a human client: `ui` or `user`, alone or followed by `:`, `-` or `_` (e.g.
     `ui:laptop`). Names that say nothing ("cursor", "claude-desktop") get 422 for those scopes.
   - With the explicit field, `client_kind_for_name` / `declares_human_client` are replaced by
     the field, and `approvals:write` is allowed only for `client="ui"`.
   - The kind is persisted in the new column `api_keys.client_kind`.
   - A DB CHECK (`api_keys_mcp_never_privileged`) makes an MCP key with `approvals:write` or
     `admin` impossible.
   - `authenticate_api_key` and `effective_scopes` strip those scopes as well (defense in depth).
   - With the explicit field, only `client_kind_for_name` needs to change.
2. **Citation `title` and `snippet` are untrusted source text.** They are not model output, so
   they are NOT run through the OutputSanitizer. Clients must render them as plain text.
   Recommendation: document this in `ragforge_contracts.api.Citation`.
3. **Tool-call `args` are sanitized model output.** `tool_call.args` and
   `interrupt.pending[].args` have every string leaf passed through its own OutputSanitizer
   (allow-list replayed); keys, numbers, booleans and null are unchanged. Clients must still
   render args as plain text / JSON, never as markdown. Recommendation: say so on
   `ragforge_contracts.sse.ToolCallEvent`.
4. **Scope semantics (DESIGN section 9/10 + ADR note).** `Scope` is frozen, so E2 splits
   administration without a new scope:
   - **tenant self-administration** (mint/list/revoke keys, `GET /v1/audit`) needs a
     *key manager*: `approvals:write` OR `admin`. Both are human-only (never on MCP keys), so an
     agent can never manage keys. Owner keys from `POST /v1/tenants` qualify.
   - **platform provisioning** (`POST /v1/tenants`) needs `admin`, issued only by the CLI with
     `--platform-admin`.
   - Proposed cleanup when the contract can change: a dedicated `keys:manage` (tenant) scope and
     `platform:provision` instead of overloading `admin`.
5. **ADR-0013 amendment:**
   - `authenticate_api_key(prefix, sha256)` returns `(api_key_id, tenant_id, user_id, scopes,
     client_kind)`. It returns no rows for unknown, wrong, revoked or SYSTEM-tenant keys.
   - `provision_tenant(...)` returns `(tenant_id, user_id)`. It writes the
     `tenant.provisioned` audit row itself.

## 3. Seam notes for other modules
- **D (AgentRunner):** for a new chat (`conversation_id` null), the API **creates the
  `conversations` row itself** (tenant, user, collection_ids) and then calls
  `run_turn(principal, <new id>, ...)`.
  - Why: the API must report the new id on `interrupt` / `error`, even if the turn fails before
    D yields `TurnDone`.
  - So `run_turn` always receives a non-null id from the API. D must treat an id with no
    checkpoint history as a fresh thread.
  - `TurnDone.conversation_id` should equal the id passed in.
- **D:** the API does its own pre-checks and answers 404 when they fail:
  - the conversation belongs to the caller: `conversations.user_id = principal.user_id` under
    RLS;
  - the approval run is visible: a `pending_approvals.run_id` row joined to the caller's
    conversation.

  After that, D still enforces the lease and pending status. When existing-conversation and
  resume streams raise `TurnInProgress` / `NotFound` before their first event, the API returns
  them as HTTP 409 / 404 problems. Errors after streaming begins become an `error` SSE event.
- **D:** `TurnDone.conversation_id` is not trusted for a new conversation: the API reports the
  id of the row it created and logs `agent_reported_other_conversation_id` on mismatch.
- **D (resume must re-emit sources):** `POST /v1/approvals/{run_id}` builds a FRESH mapper, so the
  sanitizer allow-list starts empty. **D must re-emit `TurnSources` (all hits retrieved earlier in
  the run that the answer may link to) after resume, before any `TurnText`.** Otherwise links to
  those hits are defanged (fails safe, but legitimate citations lose their links).
- **D:** the API closes (`aclose()`) the TurnEvent iterator on client disconnect and at the end
  of the stream, so the agent can release its run lease.
- **A/C (job kinds enqueued by the API):** the worker must dispatch these. Payload is a pure
  function of the dedupe key.

  | kind | priority | payload | dedupe_key | connector_id |
  |---|---|---|---|---|
  | `sync_connector` | interactive | `{"connector_id": "<uuid>"}` | `sync_connector:<id>` | **unset** (Phase 2a) |
  | `delete_connector` | maintenance | `{"connector_id": "<uuid>"}` | `delete_connector:<id>` | **unset** (Phase 2a) |

  Phase 2a integrator decision: `connector_id` is set only on jobs that count against the
  per-connector in-flight cap of 2 (`sync_page`, handoff A). A listing or delete job holding a
  slot would halve page throughput, so the API no longer sets it on these two kinds.

- **A:** `GET /v1/jobs/{id}/events` uses the `NOTIFY rf_job_progress` payload only as a wake-up.
  The payload is the job id as text, and the stream re-reads the row under RLS. Polling (2 s) is
  the correctness path. The stream ends on `done` / `dead` / `superseded`, or when `finished_at`
  is set. It also ends (silently) when its API key has been revoked (re-checked every
  `reauth_s`, 30 s).
- **C:** `DELETE /v1/documents/{id}` inserts the exclusion and tombstones the document
  (`deleted_at`) in one transaction. Sync must skip excluded items (it already plans to).
  `?forget_exclusion=true` deletes the exclusion so the next sync re-indexes the page.
- **C:** connector tokens are sealed with
  `associated_data = b"connector:<tenant_id>:<connector_id>"`. `DELETE /v1/connectors/{id}` sets
  `status = 'deleting'` and NULLs both secret columns immediately.

## 4. Not implemented (left for later phases)
- `POST /v1/collections/{id}/files` (uploads). It needs the `BlobStore` port in the container
  plus an agreed upload job kind and payload with C.
- `POST /v1/webhooks/notion` [A] and `/metrics`.
- No rate limiting of failed authentication attempts. The key space (256-bit secrets) makes
  guessing infeasible, but a per-IP limiter would cut log noise.

## 5. Scope map (for UI/MCP authors)

| scope | endpoints |
|---|---|
| `admin` | `POST /v1/tenants` (platform provisioning); also a key manager over the whole tenant |
| `approvals:write` **or** `admin` (key manager) | `/v1/api-keys` (create, list, revoke), `GET /v1/audit`; without `admin` only the caller's own user's keys are listed/revocable |
| none (any valid key) | `DELETE /v1/api-keys/{own id}`: a key can always revoke itself |
| `write` | create collections and connectors, connector sync/delete, `DELETE` documents and exclusions |
| `read` | GETs on collections, connectors, documents, exclusions, jobs (+ events); `POST /v1/query` |
| `chat` | `POST /v1/chat` |
| `approvals:write` | `POST /v1/approvals/{run_id}`; never on MCP keys |

- Keys can only mint keys with a subset of their own scopes.
- Provisioned owner keys get `read, write, chat, approvals:write`.
- Only the CLI issues `admin`, and only with `--platform-admin`.
- `approvals:write` / `admin` on an API-minted key need a `ui:` / `user:` key name (see 2.1).

## 6. Migration 0006 additions
- `documents_live_tenant_created` on `documents (tenant_id, created_at DESC, id DESC) WHERE
  deleted_at IS NULL` and `audit_log_tenant_id_desc` on `audit_log (tenant_id, id DESC)`: one
  index per keyset page, so `GET /v1/documents` and `GET /v1/audit` are index range scans. The
  queries also carry an explicit `tenant_id = :tenant` predicate (redundant with RLS) so the
  planner always uses the leading column.
