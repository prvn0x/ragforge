### Migration 0013: `rf.connector_freshness`
- Per connector kind: `connectors`, `oldest_success_at`, `oldest_success_age_seconds` — the age of the STALEST enabled connector's last success (`min(last_success)`). No tenant ids.
- **Authoritative source:** a `sync_connector` job in state `done` that carries the `listed` progress marker, in `rf.jobs` or `rf.jobs_history`. The marker matters: `handle_sync_connector` also completes the job `done` WITHOUT listing when the connector is not active (`_complete_noop`, progress `{"skipped": ...}`), and `POST /v1/connectors/{id}/sync` accepts an `error` connector, so a "sync now" click would otherwise reset a broken connector's age to ~0 and mask the alert (tested; review round 1). A positive marker also fails safe for any future no-op path. Both partial indexes carry the same predicate. It is the only record written on EVERY successful poll (the handler completes the listing even when nothing changed); `sync_cursors.updated_at` only moves when a listing returns an item, so it would call a quiet workspace stale. Listing jobs leave `jobs.connector_id` NULL, so the join is on `payload->>'connector_id'` AND the job's own `tenant_id` (a foreign payload can never freshen another tenant's connector; tested).
- "Enabled" = `active` or `error` (an errored connector is the one that needs the alert). Never synced, or older than the 30-day history retention: counts from `created_at` (only ever staler).
- **Shape (ADR-0013):** NOT a second RLS-bypassing view. A `SECURITY DEFINER` function `rf.connector_freshness_rows()` (pinned `search_path = pg_catalog, rf, ext, pg_temp`, `REVOKE ALL FROM PUBLIC`, EXECUTE to `rf_metrics` only) behind a `security_invoker` view, SELECT to `rf_metrics` only. So `queue_stats` stays "the ONE view allowed without security_invoker" and `test_catalog_invariants.py` passes unchanged. rf_metrics can read the view but not `rf.jobs`, `rf.jobs_history` or `rf.connectors` (tested); rf_api / rf_worker / rf_backup cannot read or execute it (tested).

## Seam notes: where the locked catalogue was not enough
1. **No slot for collector failures.** The task asks for "absent gauges + a counter"; the catalogue has no counter for it, so `ragforge_metrics_collect_errors_total{source="queue_stats"|"connector_freshness"}` is the ONE metric outside the catalogue (a test pins "catalogue + exactly this one"). OBS-STACK's "dashboard uses only catalogue metrics" test is unaffected (the board does not query it). A catalogue revision should add it (and an alert `increase(...[15m]) > 0`).
2. **Label values the catalogue does not list** (OBS-STACK raised the same): `priority` = `JobPriority` names; `provider` = `LLMProvider` values or `other`; `process` = `api`/`worker`/`other`; `pool` = the engine's role (`api`, `worker`); interview `endpoint` = `question`/`grade`, `source` = `notes`/`general`, `outcome` = `ok`/`no_notes`/`exhausted`/`rejected`/`error`; `kind` and `connector_kind` = code constants (shape-guarded). They live in `metrics.py` as constants; a `Metric.values` field in the catalogue would make them shared.
3. **`NOTION_STATUS` has no class for 1xx/3xx** (the API never sends them): they count as `4xx` (the request did not succeed).
4. **`VERIFICATION_STATUSES` has no `other`**: a status outside it (e.g. a leaked `pending`) is recorded as `other`, which OBS-STACK's value check would flag if a panel ever selected it; none does.

## Known gaps (honest)
1. **Orphan hits** (`ragforge_retrieval_orphan_hits_total`): counted as returned hits of a collection that NO active embedding space serves (keyword-only, unsearchable vectors: an unflipped/retired space, or a blue/green flip racing the turn), read from the same `active_spaces` query `spaces_for` already made (no extra query). DESIGN §7.3's sharper meaning (a chunk whose embedding was GC'd) needs `keyword_search` to return a has-vector flag from SQL (`adapters/db/search.py`, module B's), then one line in `agent/retrieval._count_orphans`.
2. **`dead` vs `failed` is predicted** (`permanent` or `attempts >= 8`, the `rf.jobs.max_attempts` default no code path overrides), because `PgJobQueue.fail` discards `rf.fail_job`'s verdict. A fail that lost its lease (`'lost'`) is still counted, and a `complete` whose transaction later fails to commit is counted `done`. Both are rare; the DB `ragforge_jobs_dead` gauge is authoritative. Fix: `PgJobQueue.fail -> str` (module A), then `ObservedJobQueue.fail` maps it.
3. **Surface of a chat turn** is resolved from the tenant id that `deps.authenticate` binds into the request's structlog context (I do not own `deps.py`/`ask.py`). Cleaner, and a one-liner for the deps owner: in `deps.authenticate`, also `prompt_context.surface.set(...)` from a cached tenant lookup, and drop the lookup from `chat_stream.turn_meter`.
4. **LLM timeout vs server** for the base `ChatModelError` matches the adapters' fixed messages (`"model provider timed out"`, `"... unreachable"`, `"... returned HTTP 5"`); `test_obs_metrics_llm` drives the REAL Ollama and Gemini adapters through `httpx.MockTransport` so a reworded message fails CI. A `ModelTimeout(ChatModelError)` subclass in the adapters (module D/G) would remove the string match.
5. **Not measured:** the LangGraph psycopg pool (`bootstrap._langgraph_pool`; my bootstrap scope was the chat wrapper only — one `set_function` on `pool.get_stats()` would add it as `pool="langgraph"`); per-model series are not pre-created (labels depend on config), so the very first rate-limit after a restart is the "born inside the window" case OBS-STACK's rules already handle.
6. **Redaction of stdlib logging (fixed after the final review, P1-2).** This gap said the access log was off via `log_config=None`. It was not: `log_config=None` only stops uvicorn from configuring logging, so `uvicorn.access` lines still reached stderr through flashrank's `logging.basicConfig(level=INFO)`, unredacted, along with every httpx/LangGraph/SQLAlchemy record. Now `configure_logging` installs one root handler (`structlog.stdlib.ProcessorFormatter` through the same `_RedactingRenderer`), so every stdlib record is the same JSON line and masked, and a later `basicConfig` is a no-op. `apps/api/main.py` passes `access_log=False` (`UVICORN_OPTIONS`); `uvicorn.error` stays. The token shapes also gained URL userinfo passwords (`scheme://user:[REDACTED]@`) and `Basic <base64>`. httpx/httpcore are held at WARNING (their INFO is one line per outbound call, URL included). Tests: `test_obs_metrics_logging.py` (stdlib records, tracebacks, basicConfig before and after, the level) and `test_obs_metrics_server.py` (`access_log is False`).
7. **`ragforge_jobs_oldest_queued_age_seconds` counts jobs waiting in backoff (for OBS-STACK's alert; its help text now says so).** `rf.queue_stats.oldest_queued_at` (migration 0002, module A's view) is `min(enqueued_at)` over `status='queued'` with no `run_after <= now()` filter, and `enqueued_at` survives retries. So an interactive job deferred by a Notion 429 `retry_after`, or backing off after a failure, raises the interactive age while the queue is healthy. The R2-4 rule "interactive oldest age > 120 s for 5 min" should therefore be read together with `ragforge_jobs_ready{priority="interactive"} > 0` (`ready` IS `run_after <= now()`-filtered), e.g. `max(ragforge_jobs_oldest_queued_age_seconds{priority="interactive"}) > 120 and on() sum(ragforge_jobs_ready{priority="interactive"}) > 0`. The exact fix is a ready-only age column in a `queue_stats` revision (module A's call), then the collector maps it.
8. **A cancelled model call is `interrupted`, including the extras timeout.** `asyncio.timeout(EXTRAS_TIMEOUT_S)` in the extras node cancels the stream, and inside the wrapper a cancellation from a deadline cannot be told apart from a client going away, so a slow provider on extras shows up under `outcome="interrupted"`, not `timeout`. Provider timeouts the ADAPTER raises (`model provider timed out`) are `timeout` as before. Read a rise in `interrupted` for `prompt=~"extras_.*"` as provider slowness.
9. The worker also exports the API-only unlabelled series (`ragforge_chat_streams_in_flight`, `ragforge_retrieval_orphan_hits_total`) at 0; dashboards scope by `job`, so this is cosmetic.
